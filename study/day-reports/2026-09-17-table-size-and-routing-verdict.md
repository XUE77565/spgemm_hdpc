## 1. 上午:第一刀(争用常数修正)被行分布重放证伪

### 背景
study/22 冻结计划的第一刀:`CONTENTION_BYTES_PER_DUP_MILLI` 12B→0-2B,"crankseg 型重行自动流向
dense,1.355 差距整段消失"。依据是一笔"dense 86KB < hash 98KB"的裸账。

### 证伪过程
用默认门参数(occgate=1/spanf=16/est_min=1024/win=−1/cmp=off)离线重放三阵 hash 行分布
(`/tmp/rt_cur_*.txt`,格式 `row kc flop est span ov rt`):

| 阵 | hash 行 | occgate 挡(est×16<span) | 超档地板挡 | dup 门挡 |
|---|---|---|---|---|
| crankseg_2 | 51,312 | **69%**(35,214) | 30%(15,435) | **1.1%(576)** |
| c-64 | 7,214 | 4% | **96%**(dup 中位仅 1.3) | 0 |
| F2 | 71,505 | 2% | 80% | 18%(但 span 70K,dense 裸账 570KB≫hash 73KB,挡对了) |

三个致命点:
1. **12B 常数不在阻断路径上**:SROUTE 默认 0(死路);dup 门挡的行也早被字节模型判该留 hash
2. **"86KB<98KB"是种群混用**:10620 是 dense 行的 span;hash 行 span 中位 **58K**(近全宽),
   实账 dense 471KB ≫ hash 98KB
3. **重行→dense 已是现状**:crankseg 中位行(flop 46719≥16K ∧ dup 27.5<64)本就过 dup_ok 第二支

occgate 与超档地板两门皆有实证(occgate 默认开 = 当年 17 阵电池 crankseg −16%)。

## 3. 下午:机制解剖——est 是五门全局耦合变量(路由轮盘)

### in-2004 +58.7 的验尸
- 相位对比:dense_direct **6.6→51.2ms(+44.5)**是全部涨幅;accumulate 反而 −1.8
- DD_ROWTIME 实锤:**dense_direct 人口 10,380→20,990 翻倍**
- 溢出仅 82 行(全局 1.33 有 3,285 行反而赢)→ 排除 retry 主因

### crankseg −8.5 的验尸
中位行 off est 4300(过 occgate→dense 候选)→ 模式 1 est 3440,3440×16=55K < span 58K
→ **被 occgate 踢回 hash,而 hash 本就是这些行的赢家**。赢在人口迁移,不在表长。

### 结论
est 喂五类门:occgate / diter 地板 / direct 经济学 / heavy 阈值 / bin 梯。
在估计器上乘 f(E) = 同时开五个轮盘。→ 实现解耦版(模式 2)。

### 模式 2(解耦)实现与判决
`tbl_target_rexp()`:est/路由逐位不动,仅 compute_bucket_kernel 的 4 处表长目标折减
(E>4096 阶跃 1.4,env `HASH_REXP=2`)。作用域坑:估计器段在 `if(!pfuse)` 嵌套域,
`est_expand_final` 函数级透传 + launch 侧独立解析同源 env。

电池(×5):crankseg **−0.1** / nd24k **+0.1** / c-43 +1.0 / F2 +0.1 —— **纯压表收益≈0,
全部大赢面确系路由轮盘**。但 in-2004 仍 +48.3,换通道:
**accumulate 21.1→49.5ms** —— E>4096 怪物行表压到 0.78×est,est +30% 误差带 LF→0.85+,
dup 25 的行 15 万次插入 ×4.5 链长。**重带压缩被插入流量物理否决**。
中带单独筛(E 256-4096→2.0×):crankseg −3.4 薄利 vs F2 +4.1/c-43 +13.7 净负。

**判死 commit `17db685`(论文级负结果)**:
- 表长不是瓶颈(当时口径);U 谷无全局点的真因 = 门跨越伪影
- est 是五门全局耦合变量
- REXP 两模式在库默认关(值级 4/4 + 有序 4/4 全绿)

## 5. 夜间:纯 kernel 度量定谳(用户方法论,当日最重要的实验)

### 用户纠偏
"你的实验不够纯粹,我们就是要优化 hash kernel……就都用我们的 hash kernel,只是表长不一样,
这样一测不就一目了然了" + 三阶段路线钦定(纯 kernel → 新 kernel 覆盖 → 路由设计)。

### 纯实验设计
- 行种群固定:各阵当前 hash 行
- 指标:**kernel 内 clock64**(HASH_ROWTIME Σ行周期)——dense/sort/compact 全部不混入
- 单变量:表长统一折减系数(解耦机器 `ELO=EHI=1` = 全行统一,路由逐位不动)

### 结果一:kernel 内(逐行延迟)——表长强单调
| 阵 | ×0.739 | ×0.778 | 默认 | **×1.22(加大)** |
|---|---|---|---|---|
| crankseg_2 | +45% | +40% | 10.65G cyc | **−25%** |
| F2 | +36% | +35% | 4.18G | **−12%** |
| web-Google | +18% | +14% | 5.95G | **−13%** |
| c-43 | +30% | +30% | 0.069G | **−17%** |

(溢出行数四配置不变 → 纯链长效应,非表满效应)

### 结果二:wall 终验——占用对消完全,双向皆亏
| 阵 | 每行延迟 ×1.22 | **wall ×1.22** | wall ×1.67 |
|---|---|---|---|
| crankseg_2 | −25% | **+4.7%** | +12.5% |
| F2 | −12% | +3.1% | +17.8% |
| web-Google | −13% | +1.2% | +6.2% |
| c-43 | −17% | +1.0% | +0.8% |

### 定谳(三层口径全部对齐)
1. **kernel 内**:大表链短,每行快 12-25%,单调
2. **wall**:大表 → 块 SMEM 升档 → 同驻块减半 → 延迟红利被占用吃光还倒贴;
   压表方向同样对消 + 链爆风险(in-2004)
3. **默认 2.7×/1.8× 配置 = wall 最优,双向验证**。"表长无效应"升级为
   **"两条相反单调线(latency↔occupancy)正好对消"** —— 论文素材
4. **下一刀由此指出**:破对消 = 同表长(同占用)下缩链 —— Robin Hood / 双选择 /
   散列混合变体 —— 恰为①阶段纯 kernel 工作
