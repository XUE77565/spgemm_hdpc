# 路由决策空间整理:四类分类法与处置方案

> 11-02 用户钦定整理。背景:hash 内核单文件 env 旋钮 **132 个**
> (spgemm_kernel_hash.cu grep 实测),dense/struct/merge 侧另有 20+。
> 历史成因:每把刀自带一个逃生门,从不回收。本档给出分类学与逐类处置。

## 一、问题的量化

```
env 旋钮总数: ~150+(跨文件)
其中真正参与"每阵都活的决策"的: ~10
已证纯劣/判负/实验残留: 待审计(估计 >60)
```

"碎"的根源不是决策多,是**四类性质完全不同的东西共用了同一种存在形式(env 开关)**,
从未分类回收。

### 第Ⅱ类:该固化的机制(默认≈oracle 已证 → 转正删旋钮)

11-02 消融定谳(66 阵 658 行)的直接推论——另一边是纯劣解:

```
HH_SORTED(sorted 直拷)      HASH_LHT23(折叠)      CSORT_CNT
HASH_BLK_LADDER            COMPACT_FLAT            est_expand 默认档(1.8)
```

**处置:逐个转正流程(真值对比+回归电池)→ 删 env 或留只读 → 代码常量。**
它们不是选项,是算法本体。

### 第Ⅲ类:护栏(正确性/安全,永不路由)

```
溢出保护与 retry 语义      大 smem opt-in(E3 全家块)
容量帽/占用检查            TB_TAG 实例分离 + check_disjoint.sh
全部逃生门(=0 回退)        素数档位(16253/5449/2719=数学事实)
```
**处置:单独文档化,冻结,永不进任何路由系统。**

**处置:P1 审计周逐个判死刑→删除;git 历史即档案。**

## 三、整理后的终态

```
现在:  ~150 个 env 旋钮平铺,四类混杂,没人能全说清
终态:  Ⅰ类 ~10 个 → AI Router 逐层接管(dense T 系优先→方法层影子评估)
       Ⅱ类 ~8 个  → 固化为常量
       Ⅲ类 ~10 个 → 护栏文档,冻结
       Ⅳ类 ~120 个 → 审计删除
剩下活跃 env: 逃生门 + 护栏 + AIROUTER/RTABLE 两三个总开关
```

## 四、与论文的关系

本分类法直接构成 §5 的开场素材:
- 分层测绘(11-02)= "Ⅰ类里哪些值得路由"的数据依据
- 漂移实验 = "Ⅰ类为什么该自动化"的证据
- Ⅱ类固化 = "我们连自己的旋钮都回收"的工程完整性展示
- 132→~15 的削减 = maintainability 的可量化指标

**一句话:碎是因为历史不分类;分类之后,路由系统终态里"调优旋钮"这个物种消失。**
