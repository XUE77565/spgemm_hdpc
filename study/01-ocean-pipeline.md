# Ocean 的计算流程(小白版脉络梳理)

> 背景:SpGEMM 要算 C = A×A。矩阵用 CSR 存(每行的非零元素按列号排好)。
> 核心难题:**每一行 C 的输出可能又长又乱**,得选一个"边算边去重"的策略——
> 用 hash 格子?用 dense 数组?还是干脆全局 hashmap?
> Ocean(SC'23 系工作)的答案之所以被公认为优雅,不在于某个 kernel 快,
> 而在于**整个决策系统只有一层判断,且每个常数都能查到硬件出处**。

---

## 全景图:三层结构

```
① 估计层:每行输出大概多长?(est)
        ↓
② 分路层:【唯一的一次比较】→ 走 dense 路还是 hash 路?
        ↓
③ 路内分档:dense 侧 5 档 / hash 侧 6 档,档档联动;
            怪物行 → largest 全局混合表兜底
```

---

## 第①层:估计(est)

算之前谁也不知道 C 的第 i 行有多少个非零。Ocean 先做一遍**廉价估计**:
对每行抽样/计数,得到一个 `est`(这行输出 nnz 的估计值),允许带一个 expand 修正系数。

为什么需要它:后面所有决策都要知道"这行的输出有多大、它的窗口/表要开多大"。
**est 是决策的货币,不是最后的结果**——算错了顶多路选得次优,不影响正确性。

---

## 第②层:一次比较定去路(精华所在)

大多数人会这样设计:"dense 有 dense 的参数,hash 有 hash 的参数,各判各的"。
Ocean 不是。它把两个候选**换算成同一种货币,再做一次减法**:

**同一条 SMEM 预算梯**:把 GPU 每个 SM 的 128KB 共享内存,按并发档位切:

```
并发档位(块/SM):   32     16     8      4      2
每块预算:          4KB    8KB    16KB   32KB   64KB
```

然后把每行 C 的两个"尺寸"投影到这条梯上:

- **dense 视角的尺寸 = span**(输出列的跨度):`预算 ÷ 9B/列`(val 8B + 位图 1bit 摊 1B)
  → 能装下我的窗口,最低需要第几档并发?→ `dense_bin`
- **hash 视角的尺寸 = est**(输出个数):`预算 ÷ 12B/槽`(col 4B + val 8B)
  → 我的表最低需要第几档?→ `hash_bin`

**判决:`dense_bin ≤ hash_bin` → 走 dense;否则走 hash。**

一句话翻译:"**如果这行的 dense 窗口,能住在不比它的 hash 表更贵的档位里,就用 dense**"。
平局给 dense(dense 免探测,天然占便宜)。

为什么这是鲁棒的:
- 没有任何拟合常数——128KB、9B、12B 全部来自硬件手册和数据布局
- 换 GPU、换矩阵,这条规则一个字不用改
- 新增一种内核 = 给它定一个"字节数",加进梯子,不是一个 if

---

## 第③层:路内分档(档档联动)

选好路之后,不是一个大 kernel 吃所有行,而是**按尺寸分档,档档联动**:

**dense 侧**(窗口 = 预算 ÷ 9B − 4):

| 档 | 窗口(列) | 块宽 | 并发 |
|---|---|---|---|
| 0 | 451 | 64 | 32/SM |
| 1 | 906 | 128 | 16 |
| 2 | 1818 | 256 | 8 |
| 3 | 3641 | 512 | 4 |
| 4 | 7284 | 1024 | 2 |

注意:**窗口大小、块宽、驻留块数是同一个量的三种投影**(预算梯)。
小行进高并发小窗档,大行进低并发大窗档——"多大脚穿多大鞋"由同一个公式保证。

**hash 侧**:同理,表大小梯 {331, 673, 1327, 2719, 5449, 16253}(预算 ÷ 12B)。

**怪物兜底**:est 超过最大档的行 → `largest` 桶,用**全局混合 hashmap**(数量有上限,
超了挤回 hash 梯)。注意:兜底仍在体系内,不是一个体系外的特例。

---

## 它的计数/数值两遍

- **count 遍**(symbolic):位图(1 bit/列)标记哪些列非零 → 得到每行精确 nnz → 定输出偏移
- **numeric 遍**:再扫一遍乘积,位图字级 popcount 前缀直接发射,**天然有序,免排序**

dense 路的本质优势就在这:位图既当了去重器又当了排序器,hash 路还得付探测+紧凑+排序税。

---

## 总结:Ocean 的三条设计律

1. **一次比较**:所有路由 = 同一条预算梯上的一次档位比较
2. **常数有出处**:每个数最终落到硬件手册(SMEM 大小、每元素字节),没有"调出来的数"
3. **档档联动**:窗口/块宽/占用是一个预算的三种投影,不各调各的
