## 1. 主要困境

原本在APPT上的first100的benchmark上，原本的创新点"根据矩阵特征选取merge或者hash"是成立的，因为merge在小矩阵上具有
生态位。但是切换到ocean所用的337个比较大的、更有价值的benchmark的时候发现：1.原本的dispatcher全部选择hash 2.merge几乎全输。因此merge在这个bench上并没有它在first上的生态位。后来经过对hash的优化，成功追到ocean的1.3x，但是事实上我们并没有对ocean
有真正意义上的创新点，我们对着ocean代码优化更像在原本的ocean的基础上加了一个merge分支，够不上创新。

## 2. 系统流程

```
输入矩阵 (CSR)
    │
    ▼
┌──────────────────────────────────────────────┐
│ 调度器 Dispatcher(整阵级)                    │   大阵 → hash 管线(主战场)
│                                              │   小阵 → merge3 归并(cuSPARSE 兜底)
└──────────────────────────────────────────────┘
    │ hash 管线
    ▼
┌──────────────────────────────────────────────┐
│ ① 估计层                                    │   count_flop:每行乘积总数
│   MinHash 去重估计(一次构建,全管线复用)      │   est:去重后输出个数估计
│                                              │   span:输出列跨度
└──────────────────────────────────────────────┘
    ▼
┌──────────────────────────────────────────────┐
│ ② 路由层(逐行分流,多级规则)                 │   短行直出 → straggler 专路 → 小跨度直址
│                                              │   → dense/hash 主判 → 矩阵级密度 → 惰性
└──────────────────────────────────────────────┘
    ├── dense 路:方案5 精确 count → 按档位分流
    │       ├── 六档位梯 → 结构内核(位图 symbolic + popcount 前缀发射,Ocean 式)
    │       └── 超大/全幅行 → cursor 内核
    │
    └── hash 路:10 档 SMEM 表(32→16384 槽) → 开放寻址累加 → 溢出 retry → compact + sort
```

三层结构与 Ocean 同构(估计 → 分路 → 路内分档);**第②层(逐行路由)是当前与 Ocean 差距的主要所在(§5)**。

逐层对照:

| 层 | Ocean | 我们 | 对照结论 |
|---|---|---|---|
| 整阵调度 | 无(单管线) | dispatcher:hash / merge3 / cuSPARSE | 我们多一层(小阵净胜的来源) |
| 估计层 | HLL 草图估计(其论文标题 "estimation-based" 即此) | count_flop + MinHash,一次构建全管线复用 | 我们多产出**工作量维**(flop → 重复率 dup),Ocean 的一次比较看不见重复率;实测估计成本我们更低(in-2004:我们 ~1ms vs 其 HLL 3.9ms/迭代) |
| 分路层 | **一次比较**(SMEM 预算梯投影) | 逐行多级规则 → 统一成本模型重构中(v36) | **Ocean 胜,我们最大欠账** |
| 计数/数值两遍 | 位图 symbolic + popcount 前缀发射 | 方案5 精确 count + 各数值内核(BCNT 位图 count) | 同构;我们 count 相也位图化 |

| 输出有序化 | 位图发射天然有序 | hash 路 compact+sort(税,§5) | Ocean 胜 |
| 仪器与验证 | — | 逐行采数基建 + 配对测量四铁律 | **我们独有** |

## 3. 创新大点(四条)

**① 双生态位调度——唯一在大小两端都站在前沿的系统**
一个 dispatcher 按矩阵特征整阵选路:大阵走 hash 管线(对 cuSPARSE/opSparse/HSMU/bhSparse 胜率 94%/78%/95%/100%),小阵走 merge3 归并(**0.74× 净胜 Ocean 26%**,92 阵赢 66)——merge 的生态位在小阵端成立;337 上 dispatcher 全选 hash 也同样选对了,两个基准集的整阵决策都正确。
→ 载体:merge3 动态边界自适应分桶(warp 竞标赛归并 + dense 单遍;宽带族单点 2.87×)

**② Light-Symbolic MinHash 估计层**
一次构建、全管线复用的逐行去重估计(est),同时供 hash 表配给、位图档位选择、路由决策。对照:Ocean 用 HLL 草图(其"estimation-based"招牌)——同为草图,差异在**复用经济性**(我们一次构建喂三处)与实测成本(in-2004:我们估计相 ~1ms vs 其 HLL 3.9ms/迭代);再加我们独有的工作量维 dup=flop/est(§2.1)。

**③ 开放的路由空间(目的地集合可扩展)——Ocean 封闭单梯表达不了的服务,我们加得进**
路由 = 给每类行指定一个计算目的地。Ocean 的派单是**一张固定价目表查一次**(span×9B vs est×12B):优雅、鲁棒,但表上没有的服务永远上不了菜单。"全幅行"(span 超档 ∧ est 大:位图档装不下,SMEM hash 表也装不下)在它体系里**只能进 largest 全局表兜底**(全局显存探测,全系统最慢)——且其价目表按 SMEM hash 记价,从未算过"分段窗扫 vs 全局表"这场真实对决,所以兜底永远显得够用。我们的路由空间是**开放目的地集**:
- **cursor 窗口内核 = "分段搬运"服务**:窗口逐段扫过超长跨度、空段跳过、书签(cursor)记位,全程 SMEM 累加——接住 Ocean 只能兜底的全幅行(机械与部分工程承 Ocean:游标、全局溢出 getSMBufferLoc、LLB G-group 均同源;**我们独有 = 路由目的地本身 + avgB 双模 + 全 warp 并行前缀**)
- hash 10 档表(32→16384 槽)+ ADAPT_EXPAND 自适应扩张(retry 风暴消除)

代价与收口:开放集合此前以"多级规则"(门链)形式实现,决策乱;v36 统一成本模型 = 给每个目的地单独开物理价目,把"查一次"的优雅拿回来(见创新④)——**灵活与优雅可以都要**。

**④ 路由方法论:逐行周期仪器 + 零拟合物理成本模型 + 留出验证**
- **仪器**:DSN_RT / DD_ROWTIME / DUMP_ROUTING,测出每行在每个 kernel 的真实周期 → ground truth 与 **oracle 上界**(任何路由方案都能被打分"达 oracle 百分之几")
- **模型**:每 kernel 一条物理足迹公式,常数全部可溯硬件手册/数据布局(零拟合),逐行比大小定路由;28440 行 **88% 选对、达 oracle 0.968×**
- **现状**:我们可以根据这些公式，结合ML办法去做出最好的路由

## 5. 与 Ocean 的具体差距(含"kernel 是否差不多"的直接回答)

**直接回答:系统级三相位全输是事实(in-2004:累加 31.3 vs ~18.4ms、排序/紧凑 20.5 vs ~9.5ms、估计/count 8.7 vs ~4.7ms,合计 1.87× 与 CSV 互证)——但其成因大头是路由行集不同(我们 hash 路承担了他们位图路的行)+ count 架构差异(精确 count vs 估计式配给);"kernel 本身是否不如"仍未定谳,需归一化吞吐(同 bin 档 ms/乘积数)或强制同路对拍。同走 hash 的行上存 1.8× 嫌疑(hash_spa 16.9 vs hashNumeric 9.3ms,未归一化)。**

| 对比项 | 结论 | 证据 |
|---|---|---|
| 位图 kernel vs 其位图 kernel | **无结论**(in-2004 上我们位图路只承接 2.76ms 的行,样本太少);位图 vs 位图的同场对决待强制同路实验 | — |
| **整管线系统(同矩阵)** | **已对拍:三相位全输**——累加 31.3 vs ~18.4、排序/紧凑 20.5 vs ~9.5、估计/count 8.7 vs ~4.7ms;合计 61.0 vs 32.7ms = 1.87×,与 CSV 1.89× 互证;但成因大头 = 路由行集不同 + count 架构差异,**非纯 kernel 效率** | /tmp/nsys_v34_in2004 + nsys_ocean_in2004,2026-09-12 GPU1 |
| 我们 cursor vs 其 largest 全局表 | 我们赢 | c-64 0.87× / c-64b 0.88× |
| 我们 merge3 | 其无对应 | first100 0.74× |
| **同一行:我们送 hash vs 其送位图** | **结构性差 ~2.4×** | ncu 对拍机制定位(探测+排序税的宏观体现) |

差距三层定位:

1. **战场错位**:332 阵路由全部落在 hash 族(hash 159 阵 geomean 1.321 / 变体 173 阵 1.421,输率 85–89%),无一走位图路;Ocean 同集大量走位图(发射天然有序,免排序)
2. **三笔税**:排序税(compact+sort)/ 探测溢出税 / 决策精度税
3. **检验kernel**：我首先我们要检查我们的kernel是否比较优秀和便于并行，然后根据这些实验数据去做ML
