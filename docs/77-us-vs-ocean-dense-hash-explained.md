# 我们 vs Ocean:DENSE 和 HASH 到底差在哪?(小白版对照,2026-09-04)

> 背景:两边都是"逐行算 SpGEMM(C = A×A)"的 GPU 程序。核心问题只有一个——
> **一行的乘积流进来,列号乱序还带重复,怎么累加成有序的输出行?**
> 答案就是"累加器"。dense 和 hash 是两种累加器,两边各有实现,逐项对拍如下。

---

## 第〇章 先搞懂两个累加器(30 秒版)

**HASH = 一排带锁的格子,列号先"算出该进哪格"**

```
乘积 (列3, 值5) 来了 → 格子号 = 哈希(3) → 比如 7 号格
  7 号格空?  放进去
  7 号格有人且是列3?  值加上去(重复列在这里合并!)
  7 号格有人但不是列3?  往后挪一格再试(叫"探测")
```

**DENSE = 一整面墙的格子,列号直接当格子号**

```
乘积 (列3, 值5) 来了 → 直接写进 3 号格(不用算、不会撞)
代价:这行的列如果从 0 排到 10 万,你就得有一面 10 万格的墙(大部分空着)
```

一句话:**hash 省墙、费脑子(要算要撞);dense 费墙、零脑子(直接写)**。
所以"输出密、列跨度小"的行适合 dense,"输出稀、跨度大"的行适合 hash——两边都有路由按行挑。

## 第一章 HASH 族逐项对比

### 1. 一格多大?(槽宽)

| | 我们 | Ocean |
|---|---|---|
| 符号阶段(只数数) | 12 字节/格 | **8 字节/格**(把列号压缩,和别的挤在一起) |
| 数值阶段(真算值) | 12 字节/格 | 12 字节/格 |

**直观**:GPU 的共享内存(墙上最快的那块板子)就那么大——比如 48KB。
我们一格 12B 能放 4096 格,Ocean 8B 能放 6144 格。**同样的板子,他们多放 50% 的格子**,
意味着同一个 GPU 同时能伺候更多行。

**判定:Ocean 胜**。这就是 v31-② 要抄的(把列号从 4 字节压到位宽刚好够用)。

### 2. 怎么算格子号?(哈希函数)

- 我们:列号 × 2654435761(一个神奇的常数,黄金比例),再砍掉高位 → **1 条乘法指令**
- Ocean:MurmurHash3(一套 ~10 条指令的混合搅拌)→ 搅得非常均匀

**直观**:我们的算得快但搅得糙,Ocean 搅得匀但算得慢。表只装一半时(两边都这么配),
撞车率都很低,搅得匀不值 10 条指令。

**判定:微弱我们胜**(探测便宜);大表极端分布下 Ocean 略稳,算平手偏我们。

### 3. 格子数选多少?

- 我们:**2 的幂**(64/128/256…16384),取格子号用"按位与"——1 个时钟周期
- Ocean:**素数**(503/1013/2029…),取格子号用"求余数"——整数除法,几十个周期

**直观**:素数格子能让撞车分布更散(数学原因),但每次都要做除法。
我们把表故意只装半满,撞车本来就少,所以"1 条指令"赢过"更均匀"。

**判定:我们胜**(每次写格子都省几十周期,乘以几亿次乘积 = 大钱)。

### 4. 格子大小怎么跟行的胖瘦配?(档位联动)⭐重要

一行大概多少个不同输出,就该配多大的格子墙。两边的做法:

- 我们:固定几种块大小(256/512 线程),格子墙按估计配,但**块宽不随档变**
- Ocean:**七档联动**——细行配"小墙×小块×每卡 32 个块"(行多管齐下),
  胖行配"大墙×大块×每卡 2 个块"。档与档之间,块宽、墙大小、驻卡数一起变。

**直观**:像酒店分房——我们全部标间,Ocean 从青旅床位到总统套房七档,
**每种客人都住得刚好**,GPU 的每个座位都不浪费。

**判定:Ocean 胜**。这是 190 个矩阵"稳定慢 20-80%"的主因之一 = v31-③ 的靶。

### 5. 数数和算值分成几遍?怎么配墙?

两边都跑两遍(第一遍只数每行几个非零,第二遍算值):
- 我们:两遍**共用同一张墙**(一套几何)
- Ocean:两遍**各配各的墙**——数数遍用 8B 小格,算值遍用 12B 格

**判定:Ocean 胜**(每遍各自最优)。

### 6. 装不下了怎么办?(溢出)

- 我们:整个推倒,去显存开一间"按乘积数算的超级大房"重跑这行(cage15 因此吃过 16GB 内存)
- Ocean:专用的轻量补丁内核,只重算出事的那几行

**判定:Ocean 胜**(我们重炮打蚊子)。

### 7. 干完活怎么收拾桌子?(提取)

- 我们:扫一遍格子,拿到的列是**乱序**的 → 再花一道"数数排序"(csort)整理
- Ocean:按格子序/桶序直接写出,**天然有序**

**判定:Ocean 胜**(我们白付一道排序税;road 族 compact 差距的来源)。

### 8. 行内怎么分工?

- 我们:一行交给一个 warp(32 人小组);胖行用 G-group(小组再分组、每人分几条链)
- Ocean:每行分几个线程随档位变(瘦行 8 人,胖行一个块)

**判定:各有道理**——我们的 G-group 是独门(专门对付"多乘积挤同列"的争用),
他们的档位化更系统。算我们一个"机制聪明"分。

**HASH 总分:Ocean 5 胜,我们 2 胜(探测成本、G-group),1 平。**

## 第二章 DENSE 族逐项对比

### 1. 数数那遍用什么记号?(符号形态)⭐差距最大的一项

一行有多少个不同输出列,先要数一遍。怎么记"这一列来过"?

- 我们:每列一个**字节**(8 个 bit)当标记
- Ocean:每列**1 个 bit**,而且收拾时按"字"打包数(一个 32bit 字一次数 32 列)

**直观**:同样一面墙,他们的记号本薄 8 倍 → **同一面墙能盖 8 倍宽的列跨度** →
一行要扫的"窗子"少 8 倍(每换一窗就要重扫一遍乘积,窗少 = 大钱)。
收拾时他们还是 32 列一批并行数,我们一格一格挪。

**判定:Ocean 碾压**。我们已实验性移植(BCNT/DSTRUCT),还有争用问题在修。

### 2. 算值那遍每列占多少字节?

- 我们:**21 字节/列**(值 8 + 标记 1 + 前缀 4 + 游标 8)
- Ocean:**9 字节/列**(值 8 + 标记 1)

**直观**:我们的墙每列贵 2.3 倍 → 同样内存窗宽窄一半多。
但注意:我们多花的 12B 里 8B 买了一个他们没有的东西——见下一条。

**判定:Ocean 胜**(账面),但含我们主动的"游标投资"。

### 3. 换窗要不要重新找 B 的行?(游标机制)⭐我们的独门

跨度太宽的行要分多个窗算。换窗时,乘积来自哪些 B 行要重新定位:

- 我们:**记住上次搜到哪了**(smap 游标),下一窗从停点续搜
- Ocean:每窗从头二分搜一遍

**直观**:翻书找词——我们夹了书签,他们每页从头翻。
行越宽、窗越多,书签越值钱。

**判定:我们胜(独有)**。docs/30 系列的原创。部分对消了他们窗宽 8× 的优势。

### 4. 干完怎么写出?(发射)

- 我们:扫标记,半串行地排位置,顺序写
- Ocean:位图数数直接算出每列的**精确座位号**,并行直写

**判定:Ocean 胜**。

### 5. 窗宽分档 & 超大行(straggler)形态 & 瘦行小档 & 路由

- 窗宽档位:他们七档,我们单档 → **Ocean 胜**(与 hash 的第 4 条同病)
- 超大行:我们的 LARGEST(v30)= 抄他们的位图+全局值流过,已验证 c-big −63% → **平**
- 瘦行小档:两边都有,切法不同 → **平**
- 路由判据:我们用字节模型+占用门+重复度门(维度多),他们只比档位号 → **我们胜**(表达力)

**DENSE 总分:Ocean 4 胜,我们 2 胜(游标、路由),1 平。**

## 第三章 总账(一眼版)

```
我们守着的聪明:   探测便宜(2 的幂+Knuth)、G-group 分摊争用、smap 书签、路由判据维度多
Ocean 占着的便宜: 槽窄(8B)、档位联动(七档)、位图记号(1bit)、精确座位直写、轻量补丁

打得正欢的仗:
  v31-② 抄槽窄   v31-③ 抄档位联动   BCNT 抄位图(在修)   LARGEST 已抄完(c-big −63%)
  v31-④ ESC = 把我们的 csort 前移,连墙都不要了(road 族专用)
```

**一句话总结:不是谁全面碾压谁——Ocean 把三个"结构性便宜"(格子窄、档位多、记号小)占了,
我们把三个"机制性聪明"(书签、分组、判据)占了。v31 的全部意义,就是把他们的便宜
搬进我们的聪明里。**
