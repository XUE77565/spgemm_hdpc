# 我们的 merge3 是怎么算一行的?(小白版,从自适应分桶讲起)

> 30 秒背景:SpGEMM 要算 C = A×A。程序**一行一行**地算 C 的每一行。
> 问题是:C 的第 i 行 = A 的第 i 行和 A 的所有行做一堆乘法加法,乘出来的
> 中间结果**列号乱序、还有重复**(同一个列被加了好几次),要边算边去重、最后还得**按列号排好序**输出。
>
> 三种主流做法(我们的程序三种都有,按行挑最快的):
> - **hash**:开一排带锁的格子,列号算出该进哪格,撞了就挪一格
> - **dense**:开一整面墙的格子,列号直接当格子号(费内存、零冲突)
> - **merge(本文)**:把每条已经排好序的"链"**归并**成一条有序链,重复列在归并中相遇时直接相加

---

## 第一步:一行到底长什么样?

C 的第 i 行 = 把 A 第 i 行里每个非零元素指向的 A 的行,逐条拿出来乘个系数,再全部叠在一起。

```
A 的第 i 行有两个非零:  指向 A 的第 5 行 和 第 9 行(叫"链")

A 第 5 行(已按列号排好):  列2, 列7, 列15     ← 这是"链1"
A 第 9 行(已按列号排好):  列7, 列12          ← 这是"链2"

乘上系数后,C 的第 i 行 = 链1 ⊕ 链2 的合并:
    列2  ← 只来自链1
    列7  ← 链1 和链2 都有!两份相加(去重就在这发生)
    列12 ← 只来自链2
    列15 ← 只来自链1
输出天然有序 —— 这就是 merge 的全部魔法:**没有任何排序步骤**
```

关键事实:CSR 格式里每条链**本来就是有序的**。merge 家族的哲学就是"别浪费这个有序性"。

---

## 第二步:为什么要分桶?(一条链的故事)

一行可能有几十条链(比如 100 条)。一个 32 人的小组(warp)同时归并 100 条链,
经典做法是"每次从 100 个头里挑最小的"——挑一次要比较很多次,链越多越慢。

**分桶** = 先把链按**列号范围**分组,每组(桶)内部独立归并:

```
不分桶:  100 条链 → 1 个归并器 → 每步从 100 个头里挑最小(慢)
分桶后:  列 2-99 的链 → 桶0(比如 30 条链)
         列 100-199 的链 → 桶1(比如 45 条链)
         列 200-299 的链 → 桶2(比如 25 条链)
         每个桶一个 warp 独立归并,三个桶并行跑!
```

三个额外好处:
1. **并行**:桶与桶之间互不依赖,一个 warp 一个桶
2. **免边界处理**:列 7 永远只会落在列 2-99 那个桶,不可能跨桶
3. **直接拼接**:桶 0 的结果(都是小列号)拼上桶 1 的结果(中列号)拼上桶 2 的(大列号)
   = 整行有序,**桶间都不用再排**

## 第三步:自适应分桶(我们的核心机制,v2,默认开)

**问题:固定等宽分桶会摔死。** 如果列号分布歪:

```
固定等宽(0-1000, 1000-2000, ...)分 5 桶:
  某行的链全挤在列 5000-5100 → 4 个空桶 + 1 个桶塞了全部 100 条链
  → 那个桶串行慢死,其他桶闲死(实测 333SP 矩阵:固定分桶比自适应慢 4 倍!)
```

**我们的做法(逐行动态边界):** 每一行先看自己链的**实际列范围**:

```
第 i 行的链,最左列 = 487, 最右列 = 5123 → 实际跨度 = [487, 5123]
把这个跨度【均分】成 5 段:
   桶0: [487, 1387)   桶1: [1387, 2288)   桶2: [2288, 3188)   桶3: [3188, 4089)   桶4: [4089, 5123]
每一行的桶边界都不一样 —— 这就是"自适应"
```

代价:每行多花一点点时间算边界(一次扫描就能顺便算出最左最右列)。
实测这个代价远小于收益(固定 vs 自适应:bcsstk30 差 3.6 倍、333SP 差 5.2 倍、cage13 差 2.4 倍)。

> 注:还有个 v3 实验(按"每桶乘积数均分"而不是"按列宽均分"),
> 已实现(`MRG3_BOUND=3`),默认还是 v2。v3 是为了解决"链长短不均时某桶活多"的残余问题。

## 第四步:桶内怎么归并?(warp 竞标赛)

一个桶内可能有 k 条链。32 人的 warp 这样干活:

```
每人手里攥着一条链的"当前头"(当前最小的列号)
循环:
  全组投票:谁的列号最小?      ← 一条 GPU 硬件指令,32 人同时比,极快
  最小那位:把这个元素写进输出,顺手把重复列的值都加上
           然后从自己的链取下一个元素,继续参赛
  其余人:原地不动,下一轮再比
```

这就是"**单遍 k-way warp 归并**"——每个中间元素**只被碰一次**(读一次、写一次)。
对比老前辈 bhSparse 的做法(迭代 2-way:先归并链1链2,结果再归并链3,……),
数据要被反复搬运 k 次。数学上:我们 O(n×log k),他们 O(n×k)。链越多差距越大。

---

## 第五步:一行算完,怎么知道每行有多少个输出?

整个 merge3 跑两遍:
1. **count 遍**:只归并、只数数(每行最终有几个不同的列),不算值 —— 快
2. **numeric 遍**:再归并一遍,这次真算值,直接写进最终 CSR 的正确位置

(count 遍的输出让每行在最终矩阵里的起始位置确定了,第二遍就能直写,不用再紧凑。)

---

## 整个流程图(一行的一生)

```
C 的第 i 行
   │
   ├─ ① 扫一遍:找到本行所有链的最左列/最右列(顺便数每条链多长)
   │
   ├─ ② 自适应分桶:把 [最左列, 最右列] 均分成 K=5 段,每条链按列号落桶
   │        (短行兜底:乘积太少的行不分桶,直接一把归并)
   │
   ├─ ③ 每桶一个 warp 竞标赛归并(重复列相遇即相加)
   │
   ├─ ④ 桶 0 结果 ⊕ 桶 1 结果 ⊕ ... = 整行有序输出(零排序!)
   │
   └─ ⑤ count 遍数好了nnz → numeric 遍直写 CSR 终态
```

## 它在整个系统里的位置

我们的 Auto 模式有个调度器,逐矩阵决定用 hash 还是 merge3:

- **大矩阵(ocean337 那 337 个)**:hash 赢,merge3 几乎不被选中
- **小矩阵(first100 那 100 个)**:merge3 大胜 —— 实测 dispatcher 选 merge3 的 69 个矩阵里
  **赢了 Ocean 59 个,平均快 39%**(0.614×)。为什么小矩阵 merge 赢?
  因为 hash 要先付一遍"估计每行多大"的管线成本(MinHash 估计器等),
  矩阵太小的时候这个固定成本摊不平;merge3 **不需要估计**——归并本身就知道答案。

一句话:**hash 靠"猜"省内存,merge 靠"有序"省排序;大矩阵猜得起,小矩阵归并快。**
