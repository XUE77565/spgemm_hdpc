## 第一部分:我们在做什么

### 什么是 SpGEMM?

SpGEMM = Sparse Matrix-Matrix Multiplication(稀疏矩阵乘稀疏矩阵)。

想象一个巨大的 Excel 表格,里面 99% 的格子是空的(稀疏),现在要算
"这个表格乘以它自己"。GPU 是干这活最快的硬件,但怎么安排 GPU 内部
的工作,不同方案速度差 2-10 倍。

### 谁是 ocean?

ocean 是我们的对手——学术界最新的 SpGEMM 系统(2026 年发表)。
它是我们的"及格线":我们的目标是在整体性能上超过它。

### 怎么比较?

我们在 337 个不同的稀疏矩阵上跑两边的程序,计算"我们的时间除以
ocean 的时间"的几何平均值(GM)。GM < 1.0 表示我们整体更快。

**当前状态:GM = 1.22~1.27,即我们整体比 ocean 慢 22-27%。**

## 第二部分:Kernel 的进化史

### 什么是 kernel?

kernel 就是 GPU 上执行计算的小程序。每种 kernel 有自己擅长处理的
数据模式——就像不同的刀有不同的用途(切菜刀、水果刀、砍骨刀)。

### 我们造了哪些武器?(按时间顺序)

#### 第 1 代:单一 hash kernel(2026-08 初)

最初我们只有一种 kernel:hash 表法。

**原理**:每行的乘积结果放进一个"哈希表"(就像图书馆的占座系统——
每个结果有个编号,编号决定它坐哪个座位。同一个编号来第二次,就在
原座位上累加)。

**问题**:结果分布不均匀时,某些座位被反复抢——GPU 的共享内存
没有"double 加法"的原子操作,只能用"比较-交换"循环(CAS)模拟,
重复多的行会在同一个座位上排队自旋,极慢。

#### 第 2 代:多武器分化(2026-08-09)

我们发现不同行有不同的"形态",一种 kernel 不可能通吃:

| 行的形态 | 例子 | 适合的武器 | 类比 |
|---|---|---|---|
| 每行几百个数,分布均匀 | F2 矩阵 | hash_spa(哈希表) | 图书馆占座(均匀入座,一跳即中) |
| 每行几万个数,跨度大 | in-2004 | hash_heavy(重行专馆) | 大型停车场(分区管理) |
| 列铺满整个矩阵的"巨鲸行" | c-big | dense 梯子(位图墙) | 一整面墙的格子,划一格亮一格 |
| 行短且列跨度窄 | c-64 型 | cursor(游标) | 沿着书架滑过去 |
| 极小的行 | 333SP 型 | ESC(零表) | 直接数,不用占座 |
| dup≈1 且窄跨度 | bloweybq | k7(位图+直写) | 用位图标记,完全免原子 |

#### 第 3 代:关键突破——k7 kernel(2026-10-06)

**k7 是我们完全原创的 kernel,ocean 也没有这种形态。**

**核心创新**:传统方法需要对每个乘积做原子加法(因为可能有两个
乘积写到同一个位置)。k7 利用"如果每行几乎没有重复(dup≈1),
原子加法完全是多余的"这个观察:

```
第一遍(Pass 1):只标记——用 1 个 bit 标记"这个位置有值"(原子 Or,比原子加法便宜 60 倍)
第二遍(Pass 2):认领——第一个到达的线程直接写入(普通写,不是原子写!)
                后来者发现位置已被认领,就把自己的值加上去(极少数情况)
```

**效果**:bloweybq 矩阵上比传统方法快 **4 倍**。

**附带创新——count 证书**:k7 在第一遍顺便就精确数出了每行有多少
个不同的结果。这意味着不需要额外的"计数 pass"(后面会讲到这个
有多重要)。

#### 当前武器库总表

| 武器 | 擅长什么 | 对 ocean 战绩 |
|---|---|---|
| hash_spa | 中等行(256-906 个不同值) | **0.52**(快一倍!) |
| hash_heavy | 重行(跨度大) | in-2004 **0.726** |
| dense 梯子 | 巨鲸行(列铺满全阵) | 巨鲸 **0.46-0.78** |
| cursor | 窄行(跨度小,链少) | c-64 型 **0.879** |
| k7 位图 | dup≈1 且窄跨度 | bloweybq **1.34×** |
| ESC | 极小行 | msc 微行 **0.406** |
| merge3 | 小矩阵(整阵) | first100 **0.614×** |

**在 kernel 层面(逐行对比),我们其实赢了**:公平窗口下时间加权
0.952,即我们的 kernel 平均比 ocean 的快 5%。

**那为什么整体还是输?** 答案在下一部分。

## 第三部分:路由的尝试——从静态门到学习调度

### 为什么需要路由?

因为我们有 7 种武器,每行数据必须决定用哪种武器。选错了会慢
几倍甚至几十倍。**路由就是"每行数据该走哪条路"的决策系统。**

### 第一阶段:手调静态门(2026-08~09)

最初用"if-else"硬编码规则:

```
如果 est(估计的输出大小)> 2048 且 span(列跨度)够窄:
    走 dense
否则:
    走 hash
```

**问题**:这些阈值是手调的,在某些矩阵上恰好,在另一些上灾难性错。
就像用一把固定的尺子量所有东西——量桌子可以,量蚂蚁就荒谬了。

**教训**(四连证伪):单维度的阈值门无论怎么调,总有一群矩阵受害。

### 第二阶段:学习型逐行调度器——D6(2026-10-08)

我们造了一个机器学习模型来替代手调规则:

**做法**:
1. 在 48 个矩阵上,把每行在每种武器下的实际执行时间都测了一遍
   (得到 462 万行的"真值表")
2. 用 GBT(梯度提升树)训练:输入 = 行的特征(行长/乘积数/跨度等 21 个维度),
   输出 = 该行在每种武器下的预测时间
3. 部署时:每行算一遍特征,预测各武器时间,选最快的

**结果**:逐行预测精度 **85.7%**(很好!)

**但部署后**:系统整体反而**变慢了 4.5%**。

### 第三阶段:为什么学习调度器失败了?(最重要的发现)

这是整个项目最重要的实验发现:

> **逐行 kernel 执行时间 ≠ 逐行系统成本**

用一个类比解释:

```
想象你是一个交通调度员,你精确测量了每个司机从 A 到 B 的驾驶时间。
你发现"走高速比走小路快 30%",于是让 27 万个司机都走高速。
结果:高速堵死了,所有人都慢了。

问题不在你的测量(每个司机确实走高速更快),
问题在于你测量的是"单辆车在不堵的路上的时间",
而实际优化目标是"所有车一起走完的总时间"。

堵车(集体效应)在你逐车测量时不存在,但它决定了系统结果。
```

具体到我们的 SpGEMM:

| 逐行测量说 | 系统实际发生的事 |
|---|---|
| "这行走 dense 比 hash 快 30%" | 27 万行都选了 dense → dense 的"启动准备阶段"(dense_count)从 0ms 爆到 82ms → 整体反而慢了 |
| "这行走 hash 比 dense 快" | 19 万行都选了 hash → 共享内存不够用(占用崖) → 每行都变慢 |

**结论**:逐行学习调度器在这个问题上有**原理性极限**——不是因为
模型不够好,而是因为**集体效应在逐行测量中原理上不可见**。

这个否定结果是论文的重要贡献:它解释了为什么没有人成功做过
"学习型逐行 SpGEMM 调度器"。

### 第四阶段:L0 矩阵级调度(突破,2026-10-10)

既然逐行决策看不到集体效应,那就把决策提到**矩阵级别**——
在集体效应可见的粒度上做决策。

**L0 的做法**:不做逐行微调,只做"整阵选配置":

```
配置 A:全 hash(关掉 dense 路由)
配置 B:全 hash + 开 k7
配置 C:默认路由(dense 和 hash 都开)
配置 D:默认 + k7

L0 的工作:看一眼矩阵特征,决定用哪个配置。整阵一发决策。
```

**效果**(337 矩阵验证):

| 策略 | GM vs ocean | 改善 |
|---|---|---|
| 恒 C(现状) | 1.2740 | — |
| **恒 A(全 hash)** | **1.2228** | **−4.0%** |
| A/B/C oracle(每阵最优) | **1.1958** | **−6.1%** |

**关键发现:dense 路由(默认)在 149/337 个矩阵上是毒药**——
关掉它(恒 A)反而更快。这是因为 dense 路由有一个昂贵的
"启动税"(下一部分解释)。

## 第四部分:真正的瓶颈——管线太重

### 我们的管线 vs ocean 的管线

想象一条装配线(流水线)。每个"工位"(phase)完成一步操作,
然后产品传到下一个工位。

**ocean 的装配线:3 个工位**
```
[分析+估计] → [计算] → [输出整理]
   0.7ms         4ms        1.4ms
   总计: ~6ms
```

**我们的装配线:17 个工位**
```
[数乘积] → [MinHash构建] → [MinHash合并] → [est前缀和] → [路由]
  3.2ms       ~0ms            1ms            1.1ms          4.2ms
→ [hash计算] → [重试] → [计数扫描] → [压缩+排序] → [dense计数] → [dense计算]
    8.4ms                2.1ms        4.7ms       82ms(!)
→ [下载]
   总计: ~23.7ms(同一矩阵,ocean 只要 6ms)
```

**问题很清楚:不是我们的"计算"工位慢(我们的 hash 计算只要 8.4ms vs
ocean 的 4ms,差距不到 2 倍),而是我们有很多"准备"和"善后"工位,
每个都在浪费时间。**

### 三个最大的"浪费工位"

#### 浪费 #1:dense_count(82ms,最大的单项浪费)

```
为什么存在:
  dense kernel 需要知道每行精确的输出位置才能写入。
  估计器给的 est(估计值)不够精确 → 必须跑一个额外的"精确计数"工位。

为什么 ocean 不需要:
  ocean 直接用估计值分配空间,溢出了用便宜的"重试"机制处理。

代价:
  在某些矩阵上,dense_count(82ms)比整条 hash 路径(26ms)还贵 3 倍!
  这就是为什么"关掉 dense 路由"在很多矩阵上反而更快。
```

#### 浪费 #2:估计器链(9.5ms vs ocean 的 0.7ms)

```
我们用什么:MinHash(维护每行 k 个最小哈希值)
ocean 用什么:HLL(HyperLogLog,只需更新一个寄存器)

区别:
  MinHash:每个元素需要一次完整哈希 + 比较/更新 k 个值 → ~50ns/元素
  HLL:每个元素只需一次哈希 + 一个寄存器取 max → ~5ns/元素
  
  HLL 快 10 倍。代价是精度略低(对我们高重复的矩阵可能导致更多重试)。

我们的估计器链(4 个工位,共 9.5ms):
  count_flop(3.2ms) + mh_merge(1ms) + est_scan(1.1ms) + binning(4.2ms)

ocean(融合在 1 个工位里,0.7ms)
```

#### 浪费 #3:工位之间的空闲时间

```
17 个工位 = 17 次 kernel 启动 = 17 次 GPU 空闲间隙
每个间隙约 5-10 微秒,但对总时间只有 5ms 的小矩阵来说,
17 个间隙 = 85-170 微秒 = 总时间的 2-3%

ocean 3 个工位 = 3 次启动 = 15-30 微秒(几乎可忽略)
```

### 管线浪费的量化

| 浪费来源 | 小矩阵代价 | 大矩阵代价 |
|---|---|---|
| dense_count(可消灭) | 0-30% | 0-40% |
| 估计器链(可缩短) | 10-33% | 1-3% |
| 工位间隙(可减少) | 3-5% | <1% |
| **合计** | **30-50%** | **5-10%** |

**在小矩阵上,30-50% 的时间花在了"准备"而不是"计算"上。**

## 第五部分:当前差距的完整分解

从 GM 1.27 到 1.0,每一分差距来自哪里:

| 债 | 量级 | 原因 | 修法 | 难度 |
|---|---|---|---|---|
| **dense 启动税** | ~10% | dense_count 相位 | 用 est 直接分配,消灭 count | ✅ 低 |
| **估计器太贵** | ~5-8% | MinHash 链 4 个工位 | 双估计器(HLL+MinHash) | ✅ 低 |
| **相位太多** | ~5% | 17 vs ocean 的 3 | 融合 kernel | 中 |
| 路由错配 | ~4% | 选错武器 | ✅ 恒A + L0(已验证) | ✅ 已解 |
| 某些人群 kernel 慢 | ~5% | 占用/原子问题 | 深度 kernel 优化 | 高 |
| 重带 CAS 自旋 | ~5% | H100 硬件限制 | E3 集群分片表 | 高(赌注) |
| **可修合计** | **~25-30%** | | | **→ GM 0.97-1.10** |

## 第六部分:下一步计划(study/39)

### 总体思路

```
先修地基(管线减重) → 部署已验证的改善(L0) → 再试核心突破(L1/L2) → 写论文
```

### Phase 1:管线减重(修好地基,1-2 周)

**1b. 消灭 dense_count(第一刀,最大单项)**

```
现在:估计 → 精确计数(82ms) → dense 写入
改为:估计 × 1.2 安全边际 → 直接写入 → 溢出了?用已有的 retry 机制处理

效果:dense 的启动税从 82ms → ≈0ms
     更多矩阵能受益于 dense 路由
     "diter 是毒药"的问题直接消失
```

**1a. 双估计器(自适应选择)**

```
if 矩阵的重复度 < 1.5:
    用 HLL(快 10 倍,精度够用)     → ~1ms
else:
    用 MinHash(精度高,防 retry)   → ~5ms

创新点:ocean 一刀切用 HLL,我们按矩阵特征自适应选择。
这不是抄 ocean,是比 ocean 多想了一步。
```

**1c. 相位融合**

```
现在:17 个工位
目标:8 个工位(估计+路由融合为一个;压缩+排序融合为一个)

效果:减少启动间隙,减少 GPU 空闲
```

### Phase 2:L0 部署(3 天)

```
恒 A(全 hash)为默认配置 → 337 验证 → GM 预期 1.15-1.20
```

### Phase 3:L1/L2 突破尝试(1-2 周,核心创新)

**为什么这次可能成功**(之前失败了):

| 之前失败的原因 | 修复后 |
|---|---|
| dense_count 爆炸(集体效应) | ✅ Phase 1 已消灭 |
| 估计器开销大 | ✅ HLL 换装 |
| **训练标签不含集体效应** | ✅ 新标签 = C_kernel + phase_share |

**关键改进——换训练标签的口径**:

```
旧方法(失败):
  标签 = 每行的 kernel 执行时间
  问题:不含集体效应 → 模型看不到"其他行也选了同一武器"的影响

新方法:
  标签 = C_kernel(row, weapon) + phase_share(weapon)
  
  其中 phase_share 是从一次"探针运行"校准的:
    dense 的 phase_share = dense_count 时间 ÷ dense 行数
    hash 的 phase_share = (压缩+排序+重试) ÷ hash 行数
    k7 的 phase_share = 0(k7 没有额外相位)
  
  这意味着标签本身就包含了集体效应的摊账!
```

**L2 证书兜底**:

```
k7 证书(已有):flop - distinct ≤ 上限 → 安全,direct write
dense 证书(新增):估计×边际 ≥ 实际需要 → 安全,溢出走 retry
hash 证书(已有):表不满 → 安全,溢出走 retry

如果 L1 预测错了(选了错误的武器),L2 证书会在运行时发现并纠正。
这就是 "Predict-then-Verify" 的完整闭环。
```

**成功判据**:
- L1 vs 恒 A < 1.00(净赢)→ 有部署价值
- 无矩阵回归 > 10% → 证书有效

**成功概率:40-50%**(诚实估计)

### Phase 4:论文(2-3 周)

论文的核心贡献(无论 L1 成败):

1. **否定结果**:证明了逐行 kernel 时间 ≠ 逐行系统成本(集体效应)
2. **L0 架构**:矩阵级配置选择,337 验证 6.1% 改善
3. **自适应估计选择**:HLL/MinHash 按矩阵特征选择(比 ocean 多想一步)
4. **管线减重**:17→8 相位 + dense_count 消灭
5. **(如果 L1 成功)**:首个可部署的学习型逐行 SpGEMM 调度器 + 证书
6. **(如果 L1 失败)**:精确刻画了逐行调度的物理极限

**投稿目标:SC 或 PPoPP(CCF-A)**
