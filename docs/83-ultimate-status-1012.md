## 第一部分:我们在做什么

### 什么是 SpGEMM?

SpGEMM = Sparse Matrix-Matrix Multiplication(稀疏矩阵乘稀疏矩阵)。

想象一个巨大的 Excel 表格,里面 99% 的格子是空的(稀疏),现在要算"这个表格乘以它自己"。GPU 是干这活最快的硬件,但怎么安排 GPU 内部的工作,不同方案速度差 2-10 倍。

### 谁是 ocean?

ocean 是我们的对手——学术界最新的 SpGEMM 系统(2026 年发表)。它是我们的"及格线"。

### 怎么比较?

337 个矩阵上跑两边程序,算"我们的时间 ÷ ocean 的时间"的几何平均(GM)。GM < 1.0 表示我们整体更快。

**当前:GM = 1.22~1.27,即整体慢 22-27%。**

## 第二部分:PVD 调度架构(三层大脑)

### 是什么?

PVD = Predict-Verify Dispatch,决定"每行数据用哪个 kernel"的调度系统。

```
L0(矩阵级): "这个矩阵整体该用什么管线形态?"
    → 一发决策,零逐行开销
    → 例: "关闭 dense 路由,全用 hash" 或 "开 k7"

L1(行级): "这行数据用哪个武器最快?"
    → 逐行预测各武器成本,选最快的
    → 用机器学习(GBT)或解析成本公式

L2(证书): "预测错了怎么办?"
    → kernel 内部自检,发现错误当庭降级
    → 正确性不依赖预测准确
```

### 为什么需要三层?

**只做 L1 会失败**(实验证明):
- 逐行预测精度 85.7% → 部署后系统反而慢 4.5%
- 根因:逐行 kernel 时间 ≠ 系统总时间
- 类比:你精确测量了每个司机的驾驶时间,让 27 万司机都走高速 → 高速堵死 → 全体变慢
- **"堵车"(集体效应)在逐行测量中不存在,但它决定系统结果**

**L0 在集体效应可见的粒度做决策** → 有效。

**L2 证书保安全** → k7 的 count 证书:如果实际碰撞数超过预算,kernel 自己发现并降级。

### L0 的验证结果(337 阵)

| 策略 | GM | 说明 |
|---|---|---|
| 恒 C(现状默认) | 1.2740 | 当前生产 |
| **恒 A(全 hash)** | **1.2228** | **一行 env 即赢 4%** |
| A/B/C oracle | **1.1958** | L0 天花板 |

**关键发现**:diter(默认 dense 路由)在 149/337 阵上是毒药——不是 dense kernel 不好,是 **dense_count 启动税**太重(详见第四部分)。

## 第三部分:七个 Kernel 详细讲解

### Kernel 1: hash_spa(哈希表,轻中行主力)

**用什么行**: 每行去重后有 256-906 个不同结果的行。

**原理**(图书馆占座):
```
1. 估计这行有多少个不同结果 → 决定开多大的"占座表"
2. 每个乘积结果用哈希函数算编号 → 编号决定坐哪个座位
3. 同一个编号来了第二次 → 在原座位上累加
4. 全部乘积处理完 → 按座位顺序读出结果(天然有序)
```

**为什么快**: 我们做了三项关键优化——
- **est 连续化**: 座位利用率精确到 37%(不拥挤,几乎一跳即中);ocean 的利用率 57%(拥挤,平均跳 2-3 次)
- **占用刀(REG 40→32)**: 让每个 SM 能同时处理更多行 → 整体吞吐 ×2
- **counting sort**: 排序用 O(n) 计数排序替代 O(n log n) 比较排序

**战绩**: 甜点带 **0.52**(比 ocean 快一倍),胜率 98.6%。

**边界**: 高 dup(dup>8)行会 CAS 自旋爆炸——这是 H100 硬件没有 64-bit 共享内存原子加法导致的(17 种修法全灭,硬件边界)。

---

### Kernel 2: hash_heavy / SPEC99(重行专馆)

**用什么行**: 列跨度大的重行(est > 4096)。

**原理**: 给 hash_spa 加了"专用停车位"——块几何按占用调整、组自适应、三道栅栏。这些改造让重行(需要大表)不会挤占轻行的资源。

**战绩**: in-2004 行级 **0.726**(胜率 100%,53 万行样本)。

**状态**: 已翻默认(10-04 确认,八阵屏零回归)。

---

### Kernel 3: dense_struct 梯子(位图墙,巨鲸行)

**用什么行**: 列铺满全阵的巨鲸行(span > 7277)。

**原理**(一整面墙的格子):
```
1. 把行的列范围画成一面"格子墙"(每个格子 = 一列)
2. 乘一个结果 → 在对应格子上涂色
3. 同一格子来第二次 → 在格子上累加
4. 全部乘完 → 从左到右扫一遍墙 → 按顺序读出结果
```

**为什么快**: 完全不用哈希表、不用原子操作(预计算每行的精确起始位置 → 确定性直写)。

**关键设计**: 六档位梯(DENSE_TIER)按行的 span 分档——不同宽度的行用不同大小的"墙"。

**战绩**: 巨鲸带 **0.46-0.78**(ocean 在这个区间没有对位武器)。

**边界**: 中带(span 1818-7277)1.15 输——双方都在 L1/SMEM 吞吐上限,微差不解。

**重要**: dense_count 启动税——每次开 dense 路由,需要先跑一遍 O(flop) 的精确计数来决定每行该在墙的哪个位置开始写。这个"先量尺寸再砌墙"的步骤在大多数阵上比砌墙本身还贵。

---

### Kernel 4: cursor(游标,窄行)

**用什么行**: 短且窄的行(span ≤ 1818 ∧ a_len ≤ 32)。

**原理**(顺着书架滑):
```
1. 把这行涉及的 B 列区间当成一个"书架"
2. 每条输入链放一个"游标"(指针)
3. 所有游标从左到右同步滑过
4. 每滑到一列 → 处理对应乘积 → 写结果
```

**战绩**: c-64 型 **0.879**。**出了生态位就崩**(in-2004 长行 1.34)。

---

### Kernel 5: k7(双遍位图直写,dup≈1 人口)⭐ 完全原创

**用什么行**: dup≈1(几乎没有重复乘积)∧ 窄 span ∧ 短链。

**原理**(位图标记 + 直接认领):
```
Pass 1(计数): 用一个 bit 位图标记哪些列有值(atomicOr,比原子加法便宜 60 倍)
              → 标记完顺便数出精确的每行结果数(popcount)
              → 这就是 "count 证书"!

Pass 2(写入): 每个产品"认领"自己的输出位置
              → 第一个到的线程: 直接普通写(不是原子写!)
              → 后来者发现位置已被认领: 把自己的值加上去(极少数)
```

**核心创新**: 传统方法每个乘积都要做原子加法。k7 利用"dup≈1 时原子完全多余"的观察,**F64 原子操作完全消除**。

**count 证书(L2 层的实现)**: Pass 1 的 popcount 顺便给出了每行精确的结果数。如果实际碰撞数超过预算(flop - distinct > 512),kernel 自己发现并安全降级——预测错误不会导致错误结果。

**战绩**: bloweybq 甜点 **1.34×**;独立台 4×;3.23 亿条值门 rel 4.7e-18。

**ocean 也没有这种形态**——这是我们独有的。

---

### Kernel 6: ESC / 批量族 / LARGEST(微行三件套)

**ESC(零表短行)**: 极短行(flop ≤ 32)——连表都不建,直接在寄存器里数。msc 微行 **0.406**。

**批量族(batch_s)**: est ≤ 32 的微行——一个 warp 同时处理多行(减少 launch 开销)。333SP 型 370 万小行 **5.4×**。

**LARGEST(全局位图)**: 全阵最大行特护——用全局内存位图(不挤占 SMEM)。

---

### Kernel 7: merge3(小阵整阵方法)

**用什么**: 整个小矩阵(first100 系列)。

**原理**: 3 相位(读 → 归并 → 写)——直接跳过我们的 17 相位管线。

**战绩**: first100 **0.614×**(59 阵净赢)。

**为什么快**: 完全免疫管线税。我们的 17 相位对小阵是致命的(30-50% 净窗是管线开销),merge3 的 3 相位没有这个问题。

## 七武器生态位总图

```
行的人口分布(按特征):

  极短(flop≤32)  ──── ESC(0.406)
  微行(est≤32)   ──┬─ batch_s(5.4×)
                    └─ hash_spa bin0
  轻中行(256-906) ── hash_spa(0.52)←主力
  重行(est>4096)  ── hash_heavy(0.726)
  窄行(span≤1818) ── cursor(0.879)
  巨鲸(span>7277) ── dense 梯子(0.46-0.78)
  dup≈1∧窄span   ── k7 位图(1.34×)⭐原创
  小阵(整矩阵)   ── merge3(0.614×)
```

**行级总结**: 公平窗口下时间加权 **0.952(我们赢)**。

## 第四部分:真正的瓶颈——管线太重

### 核心问题

kernel 层我们赢(0.952),系统层我们输(1.22)。差距全在管线。

### 我们的 17 相位 vs ocean 的 3 相位

```
ocean(3 工位):
  [分析+估计融合] → [计算] → [输出整理]
     0.7ms            4ms         1.4ms

我们(17 工位):
  [数乘积] → [MinHash构建] → [MinHash合并] → [est前缀和] → [路由]
   3.2ms        ~0ms             1ms             1.1ms        4.2ms
  → [hash计算] → [重试] → [计数扫描] → [压缩排序] → [dense计数] → [dense计算]
      8.4ms                            4.7ms                  82ms(!)
  → [下载]
```

### 三个最大的浪费工位

| 浪费 | 成因 | ocean 怎么做的 |
|---|---|---|
| **dense_count(82ms 最差)** | dense 需要精确计数才能定位 → 每次开 dense 都要 O(flop) 扫一遍 | 用估计值 + 运行时原子计数 → 零预计算 |
| **估计器链(9.5ms)** | MinHash 4 个独立 kernel(50ns/元素) | HLL 融合在 Analysis 里(5ns/元素) |
| **工位间隙(3-5%)** | 17 次 launch = 17 次 GPU 空闲 | 3 次 launch |

### 管线精简对 kernel 本身也有好处

管线不重只是"少付过路费"——还让 kernel 跑在更好的路上:
- **L2 缓存复用**: ocean 3 相位 = A/B 矩阵数据在缓存里 → kernel 热启动;我们 17 相位 = 缓存被估计器挤出 → kernel 冷启动(慢 2-3×)
- **GPU 降频**: 相位间隙 GPU 降频 → 下一个 kernel 要重新升频
- **SM 排空/填充**: 相位切换时 SM 利用率 <50%
